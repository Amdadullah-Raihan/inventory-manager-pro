# 📋 Technical Context Report — Invoice Maker

---

## 1. Project Overview

**What the application does:** A full-stack invoice management web application for a computer hardware shop (CN Computer & Networks, Dhaka, Bangladesh). It allows creating, previewing, printing, and managing invoices, along with basic inventory/product management.

**Business/domain purpose:** Retail inventory and invoice management for a small computer shop.

**Main user roles:** Single business owner / shop manager (no role differentiation — anyone with Google login can use it).

**Core workflows:**
1. **Login** via Google OAuth or email/password (Firebase Auth)
2. **Dashboard** — view sales, purchase, revenue, and profit overview cards with a chart
3. **Create Invoice** — fill customer details, add product line items, set billing/payments, preview, save, print, or download as PDF
4. **View Invoices** — list all invoices, search, bulk-delete, view single invoice
5. **Manage Products** — add, edit, delete, search products with barcode, pricing, and stock

**Primary features:** Invoice creation with preview/print/PDF, product CRUD, dashboard analytics, dark mode, responsive design.

**Overall architecture:** Monorepo with separate frontend (Next.js 13 App Router) and backend (Express.js + MongoDB via Mongoose), deployed on Vercel (both frontend and backend as serverless functions). Firebase Auth handles authentication. No shared code between frontend and backend.

## 4. Frontend Architecture

### Router
- **Next.js 13 App Router** with the `/app` directory
- All pages use `"use client"` directive — **there are zero Server Components**
- Pages are under `app/pages/` (not the standard `app/` route convention)
- Dynamic routes: `[invoiceId]`, `[productId]`

### Rendering Strategy
- **100% Client-Side Rendering (CSR)** — every single component is marked `"use client"`
- No SSR, SSG, or ISR utilized despite using Next.js 13 App Router
- Layout (layout.js) is also a Client Component, which defeats the purpose of layouts

### Layout Structure
- `RootLayout` wraps everything in context providers → `ProtectedRoute` → drawer layout with `Navbar` + `Sidebar` → `{children}`
- Sidebar uses DaisyUI drawer pattern (responsive: drawer on mobile, persistent on desktop)

### Context Providers (nested in layout)
1. **AuthContext** — wraps `useFirebase()` hook, provides: user, Google/email sign-in, sign-out, password update
2. **SidebarContext** — sidebar collapse state + window width tracking
3. **TimeIntervalContext** — selected time interval for dashboard ("daily"/"weekly"/"monthly"/"yearly")
4. **InvoiceContext** — wraps `useInvoice()` hook, provides current invoice state for create/edit flow

### API Layer
- **No centralized API client** — raw `axios` calls scattered across components
- API base URL from `useApiUrl()` hook: env var `NEXT_PUBLIC_API_URL` or hardcoded defaults
- **No request/response interceptors**, no error handling middleware, no retry logic
- No RTK Query, React Query, or SWR

### Component Organization
- By feature/domain: `Invoice/CreateInvoice/`, `Invoice/Preview/`, `Charts/`, `Home/`, etc.
- Some components are in the right place, but there are duplicated concerns (e.g., BillingDetails.jsx and BillingDetailsPreview.jsx have overlapping `toWords` initialization)

### Theme/Styling
- Tailwind CSS + DaisyUI with a custom theme ("mytheme")
- Dark mode via class strategy, persisted in `localStorage`
- Dark mode state lives in `RootLayout` (client component) and is passed as prop to `Navbar`
- Print styles in globals.css

## 7. Authentication & Authorization

### Login Flow
1. User visits `/auth/login`
2. Can login via **Google OAuth** popup or **email/password**
3. Firebase `onAuthStateChanged` listener tracks auth state
4. On successful login, `router.push("/")` or `router.back()`
5. `ProtectedRoute` component checks `user.email` and redirects to `/auth/login` if missing

### Token Handling
- **Firebase SDK handles tokens client-side automatically**
- No Firebase ID token is sent to the backend
- Backend has **zero knowledge of authentication**

### Protected Routes
- `ProtectedRoute` component wraps every authenticated page individually
- Uses `useEffect` to check `user.email` and redirect — this causes **flash of unauthenticated content** before redirect

### User Roles / Permissions
- **None** — single user type, no roles, no admin

### ⚠️ Critical Security Issues
- Backend has **no authentication at all** — user email is sent as a URL parameter
- Firebase config (including `apiKey`) is **hardcoded** in `public/firebase/firebase.config.js`
- Anyone can call `GET /api/invoice/anyone@email.com` and access all invoices
- No CSRF protection, no rate limiting

## 17. Modernization Opportunities

### Next.js App Router
- **Convert layout to Server Component** — move providers to a client wrapper
- **Use Server Components** for static content (NotePreview, InvoiceHeader static parts)
- **Use `loading.js`** and `error.js` conventions instead of manual loading states
- **Use parallel routes** for dashboard widgets

### Server Actions
- Replace `POST /api/invoice/new` with Server Actions for invoice creation
- Eliminates need for manual API routes for mutations

### Data Fetching
- **Adopt TanStack Query (React Query)** for all server state — caching, refetching, optimistic updates
- Replace manual `axios` + `useEffect` + `useState` patterns

### Authentication
- **Verify Firebase ID tokens on the backend** — critical security fix
- Use Next.js middleware for route protection instead of `ProtectedRoute` component
- Move Firebase config to environment variables

### Folder Structure
- Flatten `app/pages/` → `app/` (standard Next.js convention)
- Create `lib/`, `services/`, `types/` directories
- Move business logic to service layer

### Backend Architecture
- Separate routes → controllers → services → models
- Add input validation (Zod or Joi)
- Add centralized error handling middleware
- Add proper aggregation pipelines for dashboard stats
- Add pagination to all list endpoints

### TypeScript
- **Migrate to TypeScript** — biggest quality-of-life improvement
- Define interfaces for Invoice, Product, User, API responses

### Performance
- Add MongoDB indexes on `userEmail`, `issuedDate`, `invoiceNumber`
- Use MongoDB text indexes for search instead of `$regex`
- Implement pagination (cursor-based or offset)
- Lazy load heavy components (PDF generation, charts)
